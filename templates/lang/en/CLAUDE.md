## Directory Structure & Purpose

- **`docs/01-basic-design/`, `docs/02-detail-design/`, `docs/03-ui/`** — UPSTREAM source of truth from the client.
  Agents MUST NEVER modify files here. When a new revision arrives, add a new versioned file + update
  `CHANGELOG.md`; never overwrite.

- **`docs/00-glossary.md`** — Japanese–Vietnamese–English domain glossary. Every agent MUST look up this file
  before naming domain variables/fields. When encountering a new business term → **append** it here before
  naming (allowed directly in the feature branch, see rule 5); never silently invent a generic translation.

- **`docs/04-decisions/`** — stores answers to every ambiguity resolved via `/speckit-clarify`
  (`INDEX.md` = fast lookup table). Agents must check here before re-asking a question that was already decided.

- **`docs/05-lessons.md`** — project-specific technical gotchas discovered during implementation (NOT
  glossary terms, NOT constitutional principles, NOT ambiguity decisions). Append 1 line, and read at the start
  of the pipeline to avoid repeating past mistakes.

- **`docs/intake/`** — output of the `design-intake` subagent, bridging Japanese specs/Figma and Spec Kit.

- **`docs/changes/`** — 仕様変更 (specification change) impact reports generated by `/design-change <old> <new>`
  (via the read-only `impact-analyzer` subagent): maps each client change → affected ACs / tasks / files / tests
  (with reasons), Spec Kit commands to re-run, and a Japanese 影響範囲 summary for the client. Run whenever
  `docs/01-03` receives a new version, BEFORE re-running the pipeline.

- **`docs/qa/`** — 質問票 (client Q&A sheets) generated by `/qa-sheet` from intake *Ambiguities*:
  `<NNN>-<slug>.md` (source, polite Japanese 敬語) + `.csv` (UTF-8 BOM for Excel, script-generated — do not edit
  by hand). Question IDs `Q-<NNN>-<ii>` are stable and never renumbered. When the client replies →
  `/qa-sheet --ingest <file>` records decisions into `docs/04-decisions/` + `INDEX.md`. See `docs/qa/README.md`.

- **`docs/traceability.md`** — 要件トレーサビリティマトリクス (traceability matrix) generated by `/traceability`
  (`python3 .claude/scripts/traceability.py generate`): links design/intake → spec ACs → tasks → source files →
  test cases and flags ACs without tests or unlinked code.

- **`docs/test-specs/`** — テスト仕様書 (Japanese test specifications) generated by `/test-spec` from `spec.md`
  Acceptance Criteria: `<NNN>-<slug>.md` (`No | 観点 | 前提条件 | 手順 | 期待結果 | 結果 | 備考`) + `.csv`
  (UTF-8 BOM for Excel, validated for 100% AC coverage via `test_spec.py`). See `docs/test-specs/README.md`.

- **`specs/<feature>/`** — generated by Spec Kit (`spec.md`, `plan.md`, `tasks.md`). Regenerable; do not hand-edit.
  If wrong, update upstream `docs/` or `docs/04-decisions/` and re-run the pipeline.

- **`.specify/memory/constitution.md`** — immutable project principles. Supersedes everything else in the Spec Kit workflow.

- **`src/`** — production source code. Follow existing patterns and do not alter architecture unilaterally.
  **Feature isolation:** feature-specific code lives in `src/features/<slug>/` (`<slug>` matches branch `NNN-<slug>`)
  so parallel features rarely touch the same files. Touch shared areas (`src/shared/`, config, router, DI container…)
  only when necessary, in small isolated commits to minimize merge conflicts. See `docs/TEAM-WORKFLOW.md`.

## Memory (Project Memory)

Pipeline agents are **stateless** — each `/speckit-*` and subagent invocation starts fresh. Project memory is
**externalized as Git-tracked files** across 5 dedicated sources:

| Source | Memory Type | Written By |
|---|---|---|
| `.specify/memory/constitution.md` | Immutable principles | `/speckit-constitution` + Steward PR |
| `docs/00-glossary.md` | Domain terminology (semantic) | Append in feature branch; EDIT → Steward PR |
| `docs/04-decisions/` + `INDEX.md` | Ambiguity decisions | `/speckit-clarify` runbook; `/qa-sheet --ingest` |
| `docs/05-lessons.md` | Technical gotchas | Append in feature branch when discovered |
| `CLAUDE.md` | Project conventions (auto-loaded) | PR |

**Recall is mandatory, not optional:** step 1 of `/design-to-code` ("Recall memory") reads and summarizes
these sources before doing anything else to prevent *context drift*.

## Running the Design-to-Code Pipeline
Run `/design-to-code` in Claude Code and provide document paths and Figma links when prompted.

**Execution model:** `/design-to-code` is an *orchestration runbook*. Spec Kit skills in `.claude/skills/speckit-*`
(installed by `bootstrap.sh`) allow model invocation (`disable-model-invocation: false`):
- **Subagent** steps (`design-intake`, `code-reviewer`, …) → invoked automatically via Task tool.
- **Spec Kit** steps (`speckit-specify|clarify|plan|tasks|analyze|implement`) → invoked automatically via
  **Skill tool**, then **paused for your review**. `clarify` remains interactive (you answer questions);
  `implement` runs only after you approve `analyze`.
- **Fallback [HANDOFF]:** if a skill is missing or blocked, the command prints the `/speckit-*` command for
  **you to paste and run**, then waits. See `docs/04-decisions/2026-10-31-runbook-auto-invoke-speckit.md`.

Sequence: **recall memory** → design-intake → specify → clarify → plan → tasks → analyze →
implement → code-reviewer → glossary-steward → security-reviewer → **test gate** → **deploy**.

**When the client sends a new design version (仕様変更):** add the new version file + `CHANGELOG.md` entry in
`docs/01-03`, then run `/design-change <old> <new>` → report at `docs/changes/<date>-<slug>.md`.

## Mandatory Rules
1. Every contradiction between basic design / detail design / Figma must be raised in `/speckit-clarify`;
   never silently pick one side.
2. Every answer from `clarify` must be recorded in `docs/04-decisions/`, not left only in chat.
3. `docs/intake/` and `specs/` are committed to Git as proof of what the agent understood when code was written.
4. **Feature ID = GitHub Issue number.** Name branches `NNN-<slug>` where `NNN` is the issue number zero-padded
   to at least 3 digits (e.g. issue #42 → `042-user-reservation`). Never pick arbitrary numbers.
5. **Shared file governance** — distinguish ADDING from EDITING:
   - **EDITING/renaming/deleting existing terms** in `docs/00-glossary.md`, and **any change** to
     `.specify/memory/constitution.md` → requires a **separate PR** approved by the steward (code-owner).
   - **ADDING a new term** (appending 1 row) to `docs/00-glossary.md` → **allowed directly in the feature
     branch**; CODEOWNERS automatically requests steward review on the PR.
6. **Prevent context drift:** sync `main` before starting a feature; when constitution/glossary changes on
   `main`, rebase and **re-run `/speckit-analyze`** to catch drift.
